## 二、地基工程：PostgreSQL + pgvector（#29 的落地选型）

backlog #29 列了 Chroma / pgvector 两个选项，**建议直接拍板 pgvector**，理由不是向量本身，而是它能一口气吃掉四个需求，让项目从"零数据库"变成"一个 Postgres 全解决"：

| 需求 | 对应 issue | pgvector 方案 |
|------|:---------:|---------------|
| 向量检索持久化 | #29 | `chunks` 表 + vector 列，替代 InMemoryVectorStore |
| 会话历史持久化（重启不丢） | C5 | `sessions` / `messages` 表替代内存 SessionStore |
| 用户画像与长期记忆 | #33 | `user_profiles` 表 + 记忆向量化，天然复用同一套 ANN |
| 语料 metadata / 时效管理 | #28 后续 | `docs` 表存 category/region/valid_until，SQL 过滤比规则 rerank 更灵活 |

**迁移策略**（保持现有抽象，改动收敛在 store 层）：

1. `Embedder` 接口不变，embedding 选型：SiliconFlow `bge-m3`（1024 维，与现有 provider 同 Key）或本地 Ollama `nomic-embed-text`；语料仅 21→百篇级，全量重嵌入成本可忽略，**不做增量更新，重建索引即可**
2. `InMemoryVectorStore` 抽出接口，新增 `PgVectorStore` 实现，环境变量开关 `RAG_STORE=memory|pg`，开发环境零依赖跑测试
3. 现有 `searchByText` 签名保持——BM25 继续在 TS 内存里算（语料规模小，BM25 不是瓶颈），**只把向量路和 metadata 过滤下沉到 SQL**（`WHERE region=... ORDER BY embedding <=> $q LIMIT k`），RRF 融合逻辑零改动
4. SessionStore 后置为第二阶段迁移，先只做 RAG——一次 PR 只动一个边界

Docker Compose（#36）顺带加一个 `postgres:16-pgvector` 服务即可，不引入第二套存储。

## 四、核心命题：凭什么比直接问豆包强

这是项目能不能"作为真实项目"活下去的关键。先承认现实：**通用大模型在"闲聊推荐"上不会输给我们**。正面硬拼对话质量是死路，要赢在通用 AI 结构性做不到的四件事上：

### 1. 数据可信、可溯源、有时效 —— 打"幻觉"
豆包回答"隆兴寺门票"靠训练语料（可能是一年前的），错了无从发现。我们：
- 每条答案带 `sources`（已有）+ **数据核实日期**（语料 frontmatter 加 `verified_at` / `valid_until`）
- 过期语料在检索层降权并在 UI 提示"该信息核实于 X 月" —— **可信任是工具属性，通用聊天做不到**
- 配套内容运营流水线：旺季前人工核价 + 半自动爬取公示公告，这是护城河，模型抄不走

### 2. 行程是"可验证的约束解"，不是文案 —— 打"拍脑袋"
通用 AI 生成的行程不考虑两地真实距离、开放时间冲突、闭馆日。我们（对接 #31 #32 后）：
- plan 生成后跑**校验节点**：同日活动地理聚类（地图 POI 距离）、开放时间 vs 安排时段、通勤时间插入——冲突项自动重排或标红
- 天气 API 参与：雨天把嶂石岩换成河北博物院并说明原因——"行程被算过"和"行程被写过"用户能感知
- 输出物是**结构化 TravelPlan JSON**（已有），因此才能编辑（#30）、导出 PDF、分享链接——豆包给不了一个可交互的行程

### 3. 记忆与个性化 —— 打"每次从零开始"
#33 落地后：用户说过"带孩子、不吃辣、住正定"，三个月后再问仍然生效；豆包的 session 记忆是产品的恩赐，我们的记忆是自己的数据。

### 4. 评估闭环 —— 把"更强"变成数字
第三节金标集扩成对比实验：同一问题跑"本项目 vs 裸大模型"，比对要点命中率/幻觉率。**没有这组数字，"比豆包强"只是口号。**

> 一句话定位：**不做"会聊旅游的机器人"，做"石家庄出行决策的数据引擎 + 行程编辑器"，LLM 只是表达层。** 通用 AI 是水平市场，我们垂直打穿一个城市——深度就是壁垒。

## 五、进一步的发展方向（backlog 之外）

按投入产出排序：

| 方向 | 说明 | 前置 |
|------|------|------|
| **P0 上线最小集** | 鉴权 R1 + 限流 R2 + #36 Docker + pg 地基 → 真实用户可访问 | 无 |
| **移动端 H5/小程序** | 旅游场景 90% 在手机；React 现有代码走 responsive + PWA 即可起步，小程序二期再评估 | 上线最小集 |
| **行程分享链接**（#30 拆出） | 生成的 plan 可发布为只读页——自带拉新裂变属性，**优先级建议提到编辑功能之前** | pg 持久化 |
| **用户反馈闭环** | 点赞/点踩 + "行程完成率"埋点 → 反哺语料优先级与 prompt；数据从 pg 里来 | pg 地基 |
| **工具调用 Agent 化** | 检索从"一次性 RAG"演进为图节点按需调工具（查天气→再检索→再规划），LangGraph 原生支持 | #31 实时数据 |
| **多城市平台化** | data/ 目录即"城市包"，配置化城市名/prompt 人设 → 保定、正定专区…验证架构通用性后再做 | 单城市跑通 |
| **B 端输出** | 旅行社/单位团建批量生成行程：API 化 + 导出 PDF 恰好是 B 端刚需 | #30 |
| **可观测性** | Langfuse（开源自部署）追踪 retrieve→plan 链路与 token 成本；比 LangSmith 便宜 | #27 |

**明确不建议做的**：自训练/微调模型（语料量级不值得）、抢通用问答场景、堆聊天功能（多轮闲聊不是工具属性的加分项）。

## 七、风险与对策

| 风险 | 对策 |
|------|------|
| 语料时效性崩坏（票价/时间错了，信任归零） | verified_at 强制字段 + 每季度人工核价清单，宁缺毋滥 |
| 单城市价值天花板 | 先验证"比通用 AI 强"的数据，再谈平台化复制；多城市是复制品不是重写 |
| LLM 成本失控 | 限流 + mock 降级链 + Langfuse 成本看板，单会话成本设熔断 |
| 免费 API 额度（高德/天气） | 缓存 + 用量告警；天气选和风/开源自部署兜底 |
